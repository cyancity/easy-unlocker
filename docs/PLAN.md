## 1. 要解决的问题

Agent（本地或云上）干活时被鉴权挡住：需要 SSH 私钥登录服务器，或需要 API Key 写进 `.env`。传统做法是人工把明文复制粘贴过去——**明文进了模型上下文、磁盘 transcript、上游服务商**，而且用户必须在电脑前。

**目标**：让用户在**只有一台手机**的情况下，通过生物识别批准，让 Agent 把事办成；**密钥明文永不进入 Agent 的上下文、不落盘、不进入模型**。

**验收标准**：用户在手机上看一句话，点批准，Agent 完成需要凭据的操作。全程无人手动搬运明文。

## 2. 核心链路

```
                        ┌──────────────────────────────┐
                        │           Broker             │
                        │        （鉴权网关）           │
   Agent ──请求────────►│                              │
                        │  存储后端（可替换）           │
                        │   ├─ Bitwarden  ← 已有用户   │
                        │   └─ 内置保险库 ← 新用户     │
                        └──────────────┬───────────────┘
                                       │ 推送
                              ┌────────▼────────┐
                              │  手机 [批准/拒绝] │
                              └────────┬────────┘
                                       │
                        ┌──────────────┴──────────────┐
                     SSH 场景                     API Key 场景
                     只回签名/短时证书             CLI 自己写入
                     Agent 得到"能登录"           Agent 得到"已完成"
```

**三个角色，各管一件事**：

| 角色 | 职责 | 持有 |
|---|---|---|
| **Agent** | 只能发起请求 | 无 |
| **Broker**（鉴权网关） | 只发放凭据；**不连用户服务器** | 密钥（或转发能力） |
| **CLI / Injector** | 只写入目标位置，写完即忘 | 无持久秘密 |

**请求必须携带**：谁在要 / 要什么 / 用多久 / 怎么用。这是用户判断该不该批的唯一依据，由 Agent 交代、Broker 自动组装成手机上一句话。

**默认 fail closed**：超时即拒绝。

## 3. 信任模型

### 3.1 分层，而不是二选一

| 层 | 位置 | 商业含义 |
|---|---|---|
| **控制面**（账号、设备、推送、审计、计费） | 中心化 | 这是能卖的东西 |
| **数据面**（解密密钥、签名） | **用户侧** | 服务商碰不到，也不该碰 |

**架构上服务商无法解密**，"要不要信任服务商"这个问题就消失了。先例：Bitwarden（云端只存密文）、Tailscale（控制面中心化、数据面点对点）、1Password、Signal。

### 3.2 手机 = 批准端 + 数据面

既然每次都要人批准，**批准的时候人本来就在看手机**。所以手机可以兼任数据面：推送到达 → 解锁 → App 本地解密 → 签名/取值 → 回传。密钥从未离开手机，且**不需要一台 7×24 常开的设备**。

代价：手机不在线 = 超时 = 拒绝（fail closed）。用户本来就要批准，所以代价接近于零。

> 例外：无人在场的自动化场景需要一台常开设备作为数据面。属于后续阶段，不进 MVP。

### 3.3 为什么"Broker 不连用户服务器"

若 Broker 自己 SSH 到目标机写 `.env`，它就从"持有密钥"升级成"持有密钥 + 所有服务器的访问权"，信任面翻倍，且用户要给每台服务器开白名单。**拆出 Injector 后，Broker 一台服务器都不连，不需要任何白名单。**

### 3.4 配对 token 的权限边界

目标机上保存的配对 token **只有"发起请求"能力，没有任何"读取"能力**。服务器被入侵时，攻击者只能不断刷用户的批准请求，读不到任何密钥。用户手机上的拒绝是最后一道闸。

## 4. 组件

| 组件 | 形态 | 说明 |
|---|---|---|
| **easyGet CLI** | 单文件可执行 | 请求端 + Injector 二合一。装在 Agent 所在机器 |
| **Broker** | 常驻服务 | 收请求、推送、等待、发放。可 Serverless（但只能做颁发，不能做注入） |
| **手机 App** | iOS / Android | 批准 UI + 本地解密 + 签名 |
| **存储后端** | 插件 | Bitwarden（已有用户，零迁移）/ 内置保险库（新用户，只存 Agent 要用的那几个） |
| **推送通道** | 插件 | APNs / FCM |

### 关键设计点

- **回签名还是回原文，由 Broker 内部按凭据类型决定，用户永远不需要选**。
  - SSH → 短时证书（约 5 分钟）或一次性签名。推荐短时证书：一次批准覆盖一段会话，避免手机被反复轰炸；安全性等价。
  - API Key → CLI 自己写入目标位置，**Agent 的模型从未见过这个值**。
- **agent 侧永远只有一条命令**：`easyGet <name> --for "<理由>"`，需要写入时加 `--write-to <路径>`。
- **CLI 主动出向连接**（WebSocket over 443），不需要在服务器上开端口、不需要防火墙白名单。

## 5. 路线图

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| **P0 — MVP** | 单用户、单机 Broker、Bitwarden 后端、手机用现成推送通道。详见 [MVP.md](MVP.md) | 用户自己能在只有手机时救回被 block 的 Agent |
| **P1 — 可用性** | 手机 App（替代临时推送通道）、多设备、审计日志、待批准队列。需求真源 [P1-APP.md](P1-APP.md) | 不依赖任何现成 bot；每次批准都有可查记录 |
| **P2 — 供应链** | 一键安装（cloud-init / 镜像预装）、多存储后端、配对流程产品化 | 新机器上零手动步骤完成接入 |
| **P3 — 产品化** | 账号体系、计费、托管 Broker、邀请制 | 非作者本人可使用 |
| **P4 — 团队/企业** | 成员与设备策略、SSO、合规审计报告、自托管发行版 | 团队版可收费 |

**商业判断**：个人版定价天花板低（开源版存在，必须便宜到"不值得自己搭"）。真正的收入在 P4 的团队能力——审计日志、SSO、成员策略、合规报告是自搭建不出来的。

## 6. 关键决策记录

| 日期 | 决策 | 理由 |
|---|---|---|
| 2026-09-13 | Broker 不直接操作目标服务器，拆出 Injector | 避免信任面翻倍，避免服务器白名单 |
| 2026-09-13 | 数据面放用户手机，而非中心服务器 | 让"服务商无法解密"成为架构事实而非承诺 |
| 2026-09-13 | SSH 走签名/短时证书，不走明文私钥 | 私钥不应传输；签名天然一次性 |
| 2026-09-13 | API Key 由 CLI 写入，不经 Agent | 值不进模型上下文 |
| 2026-09-13 | 存储后端做抽象，不绑定 Bitwarden | 新用户不该被迫先装 Bitwarden 再迁移 |
| 2026-09-13 | P1 App 不替代 Bitwarden；只存 Agent 凭据 | BW 解锁是整库会话，做不到「这一次请求 + 指纹」；autofill 是另一个产品 |
| 2026-09-13 | 传输层：手机用本次 `easyGet` 临时公钥密封，Broker 只转发 | 安装期长期 CLI 私钥被盗等于未来所有 secret；pairing token 封包则 Broker 也能解 |
| 2026-09-13 | 条目名是提示不是 ID；批准时手选，可加别名 | CLI 未必拼得出库内名称；禁止模糊自动匹配 |
| 2026-09-13 | 恢复码与密文备份是同一件事 | 一份恢复材料解开备份文件；指纹只是本机拆封 |
| 2026-09-13 | 两种解锁：请求每次一次性；浏览随 App 关闭上锁 | 逛过库不能免掉下一次批准指纹 |
| 2026-09-13 | 控制面中心化 + 客户端开源 | 兼顾商业与信任 |
| 2026-09-13 | 手机兼任数据面 | 避免要求用户有一台 7×24 常开设备 |

## 7. 未决问题

1. **SSH 的具体机制**：自建 CA 签短时证书，还是实现 ssh-agent 协议（Agent 侧接 `SSH_AUTH_SOCK`）？后者对现有工具链更透明，前者更容易做集中撤销。
2. **CA 放哪**：Broker 签（Broker 碰到私钥）vs 手机签（私钥只在手机，但手机要实现 CA）。按 3.2 的方向应选手机签。
3. **推送通道选型**：自建 APNs/FCM 需要开发者账号与证书；P1 之前可继续复用现成 bot。
4. **手机 App 技术栈**：原生（Secure Enclave / StrongBox 支持最好）vs Flutter/RN（一套代码两端）。
5. **首个非 Bitwarden 后端的形态**：内置保险库是用 SQLite + 主密钥派生，还是复用某个现成方案。
6. **失败与恢复**：手机丢失、换机、Broker 宕机时的恢复路径（备份密钥 / 恢复码）——这是密码类产品的必修课，MVP 可以先不做但要留位。
7. **是否接受无人在场的自动化**：若接受，需要一台常开设备做数据面，安全模型要重新讨论。

## 8. 调研结论（避免重复劳动）

**已确认：市面上没有现成产品完整实现这条链路。**

简要：
- **企业 PAM**（Teleport / CyberArk / Delinea / StrongDM / 12Port / Keeper）：有手机批准，但批的是**人类**的请求；对 Agent 是**刻意不做人工环路**。且全部企业合同制。
- **CIBA 族**（Auth0 / Okta / Keycloak / BKey / Descope）：有真正的推送+生物识别，但**只给批准信号，不给凭据**。Keycloak 的 CIBA 默认不推手机，要自己实现 `AuthenticationChannelProvider` SPI。
- **Bitwarden 官方 Agent Access SDK（`aac`）**：最接近，Noise 端到端加密隧道 + 人类环路，Apache-2.0 免费。但**审批在终端 TUI**，手机桥接只有 0 star 的 tmux 抓屏方案；最新版 v0.11.0（2026-03-21）后未见更新。
- **`akr`**（Akamai，前身 Krypton）：**唯一**做到"手机批准 + 私钥永不离开手机 + 标准 SSH agent 接口"的成品。但闭源、beta、绑定 Akamai MFA App、只支持 SSH。
- **个人级项目**（`aac-ntfy-bridge` 0★、`keys-on-the-wire` 28★、AILANG Secret Approvals）：推送 + 批准的收敛做法（单次 token、fail-closed）都有共识，但没有一个达到生产级。
- **明确没被解决的**：agent 向 Bitwarden 请求 → 手机生物识别批准 → agent 拿到短时凭据，这个完整闭环。`rbw` 解锁后是**全库 bearer 状态**，无逐次批准；`bw serve` 解锁后**零认证**；Bitwarden Secrets Manager **完全没有人工环路**（设计上明确"不能被 2FA 卡住"）。
